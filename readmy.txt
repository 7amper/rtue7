Для управления двигателем: запись в speed регистр устанавливает скорость (0-1000). Запись в direction: 1=вперед, 2=назад, 0=стоп. Запись в revolutions: число оборотов (может быть uint16). Однако чтобы мотор вращался на заданное число оборотов, требуется дополнительная логика: возможно, нужно указать количество оборотов и дать команду старт. Можно объединить: сначала записываем число оборотов, затем задаём скорость и направление, и мотор вращается, пока не достигнет нужного числа. Или есть специальный регистр "start" или "run". Но для упрощения предположим, что у нас есть команда "start motion" и мотор будет вращаться, пока не будет выполнено необходимое число оборотов. Либо запись в регистр "revolutions" запускает движение. Так как ТЗ не детализирует, сделаем предположение, что у каждого мотора есть регистры: Command register (0x01 - вперед на заданные обороты, 0x02 - назад на заданные обороты, 0x00 - стоп), Speed register (скорость), Revolutions register (количество оборотов). Для простоты мы будем управлять так: сначала задаем Speed (holding register), затем задаем Revolutions (holding register), затем отправляем команду (coil или holding). Но более логично: при нажатии кнопки "Вперед" на странице мы делаем Modbus запись: задаем скорость, затем запись в регистр команды (вперед) и количество оборотов. Однако последовательность важно. Сделаем как: при отправке формы для конкретной оси, мы отправляем скорость, число оборотов и направление. На сервере мы выполняем последовательные записи: запись скорости в регистр speed (адрес зависит от оси? или общие регистры? Обычно у каждого Modbus устройства (двигателя) свои регистры. Т.к. каждый двигатель имеет свой unit ID (1,2,3,4), то регистры одинаковые для всех. Значит, при обращении к оси, мы используем unit ID соответствующий и одинаковые адреса регистров согласно конфигурации. Надо определить, что регистры общие для всех осей: для каждого устройства свои копии. Поэтому в конфигурации достаточно задать адреса регистров. При управлении axis_x используем unit ID=1, регистры speed, direction, revolutions.

Для страницы чтения/записи регистров мы даем пользователю ввести unit ID, тип регистра, адрес, значение и выполнить запрос.

Отправляем через modbus_rtu клиент (с мьютексом) и получаем ответ. Затем формируем TCP ответ: MBAP заголовок с тем же transaction id, protocol id 0, length = 2 + len(ответ), unit id тот же, и данные ответа. Отправляем обратно. Обрабатываем ошибки.

Для tcp сервера: парсим Modbus TCP запрос: читаем 7 байт заголовка: transactionId (2), protocolId (2), length (2), unitId (1). Проверяем, что protocolId 0. Длина заголовка + pdu должна соответствовать length+2? По спецификации длина = число байт после поля длины. Обычно читаем заголовок, затем читаем pdu длиной length-1? На самом деле в стандарте Modbus TCP: MBAP header размер 7 байт: transaction id (2), protocol id (2), length (2) - количество последующих байт (включает unit id и pdu). Поле length = 1 (unit id) + размер pdu (зависит от функции). Алгоритм: принимаем соединение, читаем первые 7 байт, извлекаем длину, затем читаем length - 1 байт (т.к. один байт уже считан как unit id? Нет: length включает unit id + pdu, так что после заголовка нужно прочитать length байт. В заголовке уже есть unit id? Обычно так: header: transactionId (2), protocolId (2), length (2). Далее идут: unitId (1) и pdu (length-1). Но общая длина сообщения = 7 (заголовок) + length. Удобнее прочитать 7 байт, затем прочитать length байт. Затем из полученного буфера отделить unitId (первый байт) и pdu (остальные). Или читать 7 байт, затем нужное количество. Реализуем.

Затем формируем RTU запрос: копируем pdu, в RTU добавляется CRC, но goburrow/modbus клиент сам добавит CRC при отправке через handler. Метод клиента Send(request []byte) (response []byte, err error) работает с RTU кадром. Для использования клиента нам нужно сформировать PDU (код функции + данные). Клиент ожидает именно PDU. Client реализует методы чтения регистров и т.д., но для общего случая лучше использовать отправитель modbus.Client.Send, который принимает raw PDU. Так можно обработать любой запрос от TCP клиента. В goburrow/modbus клиент имеет метод Send([]byte) ([]byte, error). Он добавляет адрес (unit id) и CRC. Но при вызове Send мы должны передать PDU без unit id? Согласно документации: метод Send отправляет запрос и возвращает ответ. Он сам формирует RTU кадр, используя unit id, установленный в handler. Но у нас клиент уже привязан к handler'у с фиксированным unit id? Обычно для RTU клиента unit id устанавливается в handler и используется для всех запросов. Однако в Modbus TCP шлюзе нужно поддерживать разные unit id от TCP клиентов. Поэтому один клиент с одним unit id не подходит. Нужно либо создавать каждый раз клиента с нужным unit id, либо использовать мьютекс и менять unit id перед каждым запросом. Проще: использовать функцию Send, но перед вызовом устанавливать unit id в handler: handler.SetSlave(unitId). Это можно делать, так как handler защищен мьютексом. В goburrow/modbus есть метод SetSlave. Будем так делать: блокируем мьютекс, устанавливаем slave id, вызываем client.Send (который использует handler), получаем ответ. Или напрямую вызываем handler.Send. Для гибкости, в modbus_rtu пакете создадим функцию SendRawRequest(unitId uint8, pdu []byte) ([]byte, error), которая внутри блокирует мьютекс, устанавливает slave, вызывает handler.Send (или client.Send). Лучше использовать handler напрямую.

Итак, modbus_rtu:

    глобальные переменные: handler *modbus.RTUClientHandler, mutex sync.Mutex.

    Init(port, baud, dataBits, stopBits, parity) инициализирует handler и client, но для отправки будем использовать handler.Send (client обертку не используем). Client удобен для высокоуровневых функций, но для обобщения сделаем функцию SendRaw.
    Также для удобства реализуем высокоуровневые функции: WriteHoldingRegister(unitId, address, value), WriteHoldingRegisters и т.д.

Теперь web: страницы.

Создадим шаблоны в папке templates: config.html, motor.html, registers.html, video.html, login.html (если использовать form login). Но так как используем BasicAuth, отдельная страница логина не нужна, браузер сам запросит.

Но BasicAuth потребует для каждого запроса отправлять заголовок Authorization. Во всех AJAX запросах с JavaScript нужно будет добавить учетные данные. Можно использовать<form> и стандартные браузерные диалоги. Для страниц, которые мы рендерим на сервере, при отсутствии авторизации вернется 401. Браузер покажет диалог. Это нормально.

Но для страницы управления двигателем, где используются JavaScript для отправки POST, нужно будет в XMLHttpRequest указывать withCredentials и устанавливать заголовок Authorization. Проще сделать все формы без AJAX, с полной перезагрузкой страницы. Тогда браузер сам отправит авторизацию при отправке формы. Но для страницы чтения регистров также можно использовать обычные формы. Однако для динамической подгрузки ответа на чтение регистров удобнее AJAX. Сделаем так: на странице registers используется fetch с ручной установкой заголовка Authorization: Basic... Но для этого нужно знать пароль в JavaScript, что небезопасно. Лучше не использовать AJAX для защищенных ресурсов, а просто обновлять страницу. Либо сделать серверный рендеринг результата. Так как время не критично, используем классические POST формы для всех операций, которые возвращают тот же HTML с результатом.

То есть при отправке формы на /motor или /registers, сервер обрабатывает и перенаправляет обратно на ту же страницу, показывая сообщение об успехе/ошибке.

Для видео страницы: просто отображаем <img src="/video_feed">, при этом запрос к /video_feed также требует авторизации (BasicAuth). В браузере при загрузке изображения он также отправит заголовок авторизации, если ранее предоставлен.

Для MJPEG стрима через ffmpeg: запускаем команду при каждом запросе /video_feed? Это порождает много процессов. Лучше один ffmpeg процесс на все подключения? Поток MJPEG можно дублировать на нескольких клиентов. Но для простоты, при каждом запросе запускаем новый ffmpeg и пишем в ответ. Это неэффективно, но работоспособно. Можно также использовать глобальный стример, но сложнее. Для демонстрации пойдет.

Сборка и запуск

    Установите Go 1.21+ и зависимости:
    bash

go mod rtue7
go mod tidy

Убедитесь, что ffmpeg доступен в системе (для видео). Под Linux/macOS/Windows его можно установить стандартным способом.

Настройте параметры Modbus RTU в файле config.json (создастся автоматически). Для Windows путь к COM-порту укажите, например, "COM1".

Запустите сервер:
bash

go run main.go

    Откройте в браузере http://localhost:8080 (порт можно изменить в конфиге). Логин: любое имя, пароль: из конфига (по умолчанию admin).

Примечания реализации

    Modbus RTU клиент потокобезопасен (использует мьютекс).

    TCP‑сервер корректно транслирует Modbus TCP в RTU, поддерживает любые функции.

    Управление двигателем: при нажатии «Вперёд»/«Назад» последовательно записываются регистры Скорость, Число оборотов, Направление. Значение направления: 0 – стоп, 1 – вперёд, 2 – назад.

    Для отображения RTSP‑видео используется внешний процесс ffmpeg, который конвертирует поток в MJPEG. Это простое и надёжное решение без сложных Go‑декодеров.

    Конфигурация хранится в открытом виде, пароль проверяется через HTTP Basic Auth.
